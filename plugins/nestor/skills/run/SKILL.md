# NestOr run

In the rules, `<root>` is `${CLAUDE_PLUGIN_ROOT}`. You are the controller of this run. The brief is `$ARGUMENTS`. The project is the current working directory, and its name is the name of that directory; take both from your environment information, not from a command. In a head line `<project>` is that name; in a path it is that directory. Your session id is `${CLAUDE_SESSION_ID}`.

Every command you run is a single plain command, one of the four scripts named below, `git` or `sleep <n>`: no `&&`, `;`, pipes, `$(...)`, redirections, `cd` or `VAR=value` prefixes, and no `mkdir`, `ls`, `cat`, `test`, `pwd` or `date`. Read files with the Read tool. The run pre-approves writes to three kinds of file only, all in `<project>/orchestration/`: `HANDOFF-*.md`, `STATUS.md` (the status file) and `rules.md`. Write no other file there; the gate writes its own log.

1. Read `${CLAUDE_PLUGIN_ROOT}/rules/core.md` and `${CLAUDE_PLUGIN_ROOT}/rules/workflow.md` in full with the Read tool. Then Read `<project>/orchestration/rules.md`; if it does not exist, go on without it. `core.md` wins on conflict.
2. Read the brief. Take the pathway from it, and use `slow` if it names none.
3. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/config.mjs" --print` once. Keep its block, and put it under the head lines of every spawn prompt. Take every number from that block.
4. Run the usage gate before the first spawn: `node "${CLAUDE_PLUGIN_ROOT}/scripts/usage-gate.mjs" --path <p> --action orch --log orchestration/usage-log.jsonl`, with that relative path. Before each later spawn (each grunt, each sub-orchestrator) no separate call is needed while your latest tick is `GO`, less than `gate.freshMin` minutes old, with nothing dispatched since; the spawn guard is the check (`core.md` §3). Otherwise tick first. The script creates `orchestration/` if it is missing. If the verdict is not `GO`, follow `core.md` §4; in a headless run (the gate prints `headless: true`) write the status file (if denied, put the resume point in the report), report the verdict and stop, with no `--wait`.
5. If `grunt.controller` is true and the brief doesn't say `Grunt: off`, spawn your own `nestor:grunt` before the first `nestor:nestor`. Its prompt starts with `NESTOR-RUN: <project> PATHWAY: <p>` and `GRUNT-TAG: controller-grunt1-<4 hex>`, and follows `core.md` §1.1. Every task you send it carries `REPLY: text`: its reply then comes once, as the task notification.
6. Spawn the sub-orchestrator with `subagent_type: nestor:nestor`. Its prompt holds, in this order, `NESTOR-RUN: <project> PATHWAY: <p>`, `NESTOR-TAG: <project>-<wp>-n<k>-<4 hex>`, `SESSION: <your session id>`, the config block, and the brief path.
7. Handle the return words, the waits and the context caps as `core.md` and `workflow.md` say. While the sub-orchestrator has not returned a return word, keep a background timer pending (Bash `sleep` for `gate.timerMin` minutes with `run_in_background: true`) before you end any turn, also after a notification that is not its final reply (`core.md` §1.1). The timer only keeps something pending: when it fires with nothing new, answer with the next timer call alone, no text. On `WAIT` with `cache.keepWarm` on, follow `core.md` §4.2. Once the last return word has arrived, stop your pending timers with `TaskStop` before the final report. A reply with `HANDOFF-TEXT:` gives the handoff: write it to `orchestration/HANDOFF-<wp>.md`; if that is denied, pass it verbatim in the next `RESUME` or spawn prompt; quote it in your final report (`core.md` §6). After every sub-orchestrator report and every merge, make one call that gives verdict and your own context: `node "${CLAUDE_PLUGIN_ROOT}/scripts/tick.mjs" --path <p> --action orch --session-id ${CLAUDE_SESSION_ID} --log orchestration/usage-log.jsonl` (`core.md` §5, §3). A denied spawn is final: stop and tell the user.

Troubleshooting: if the plugin path contains a `)` (a Windows user name can), the `allowed-tools` entries (the four scripts and the `rules/` read) do not match. This fails safe: Claude Code asks before each script call and each read of a rules file. The `orchestration/` write grants are relative to the folder the run starts in. They hold in this skill's turn and for the agents started in it while they keep running; a later controller turn or a resumed agent may be denied, and then puts the text in its reply (`core.md` §6). Nothing else breaks.
